## Findings (condensed; P0 = silent data loss/corruption or permanent stop)

### GDT (main session, ground truth: GDT 2.1 spec, QMS; CGM Turbomed + PADSY docs)
- P0 Only `*.gdt`/`*.bdt` watched; spec filenames are `<Empf≤4><Send≤4>.NNN` (counter from .001) or `.GDT`. Spec: receiver must DELETE after reading; sender must not overwrite an unread `.GDT`. Agent never deletes → a conformant PVS blocks after the first file.
- P0 Satzart "8316" handled as a record type: 8316 is the field "GDT-ID des Senders". Real PVS→device Satzarten: 6301 (Stammdaten), 6302 (neue Untersuchung anfordern; required when 8402 is sent), 6311 (Untersuchung zeigen). 6302 was dropped entirely.
- P0 FK 8420 = "Ergebnis-Wert" (measurement result), was summed as invoice EUR → fake revenue. GDT carries no billing data at all. 6228 = Ergebnistabellentext (not a date), 3622 = Größe, 3628 = Muttersprache (were used as Bemerkung/phone/email).
- P0 Charset: spec default is CP437 (9206=2), 7-bit DIN 66003 (9206=1), ISO-8859-1/CP1252 (9206=3); parser only probed utf8/iso-8859-15/cp1252 and ignored 9206.
- P0 A file without trailing CRLF throws forever (never consumed, PVS blocked); no periodic rescan; no chokidar error handler; startup catch-up only once.
- P1 Local times labelled UTC. Lead token: GDT has no Bemerkung field; scan free text only for the `EINS-Lead-xxxxxxxx` token.
- Must NOT steal other devices' files in a shared GDT folder: only claim files addressed to EINS (filename prefix = receiver id, or 8315 = receiver id). 6300/6310 are device→PVS: never touch.
- GDT 3.x phone/email: 3618 Mobil, 3619 E-Mail, 3626 Telefon (BDT 6100 also 3626).

### Fixed, ranked by damage (failing test first for each)

Wrong or missing revenue / attribution:
1. **Leads never had a patient.** `requests.patient_id` was never set in production, so derive never reached a lead: no PVS status, revenue or Purchase for any lead. `server/request-patient-link.ts` (`attachRequestsToPatient`, called by derive): a PVS patient picks up unlinked non-spam requests with the same email (names compatible) or the same last 9 phone digits (only when no other patient has that phone, both names present and compatible). `first_touch_source` moves from "pvs" to the lead's source when the lead is older than the patient row (since the verifier: not for a patient whose PVS activity is more than 24 h older than the Anfrage, item 25). Linker Stage 2: a lead token on a request without a patient now creates the patient from PVS data and links the request (race-safe) instead of skipping. Deliberately no patient at intake: retention (`purge-retention.ts`) deletes only requests with `patient_id IS NULL`. Backfill: the one-time re-derive from 0091. Tests: `request-patient-link.test.ts` (14).
2. **Derive rewritten** (`pvs-status-derive.ts`): several appointments per lead summed; appointment-less invoices reach the lead through synthetic buckets; refunds summed per `pvsRefundId` and clamped per invoice; `sourceRevision` decides first; full refund = revenue 0 + downgrade; revenue without an invoice behind it reset to 0; `completed` = behandelt; stamps `patients.pvs_derived_at`, and reconcile re-derives patients with newer events (migration 0091).
3. **Storno / net-zero invoices kept their old amount forever.** CSV (agent and portal wizard) emitted nothing for them. Now InvoicePaid 0 is emitted; derive treats any drop below an invoice's peak as a refund (`peakPaidByInvoice`), so the lead is downgraded like a refund.
4. **Agent CSV picked Honorar/Netto over Rechnungsbetrag** (undercount: Auslagen such as filler or toxin, and MwSt missing). Order now: paid column, invoice total (counted once per invoice: latest positive total plus distinct credit totals), Brutto, Betrag, Summe, Honorar/Netto. `AUTO_MAPPING_VERSION` 4: auto-mapped files are re-read once.
5. **Older versions could overwrite newer ones** (retry or dead-letter requeue sends an old row after a new one; a correction moved the payment date earlier). `sourceRevision` now comes from the CSV file mtime (agent watcher) and from the DB row's modified_at (normalizer; timestamp cursors only, sentinel/pre-1970 values omitted, not part of the id hash so a bare touch still dedups). Tests: `source-revision.test.ts` (7).
6. **Purchases lost on an ads-outbox insert error.** Derive swallowed the error and stamped the patient as derived. Now the job throws after the KPI rebuild and leaves `pvs_derived_at` unset (pg-boss retry, reconcile catch-up).
7. **Revenue double counted after a patient re-link or PatientMerged.** The PVS map moved, the requests stayed on the old patient. Requests of a patient left without PVS map rows now move with it, and both sides are re-derived (`moveRequestsOfUnmappedPatient`).
8. **An older patient update overwrote newer contact data.** The agent sends a retried row behind newer ones, so an older PatientUpserted could replace a newer email or phone, which lead linking (item 1) and review emails depend on. It is no longer merged when a later PatientUpserted of the same PVS patient and source is already applied (`newerPatientUpsertApplied`, uses the existing patient index). Test: `pvs-linking.stale-upsert.test.ts`.
9. **PVS data of a patient froze for good** when its email or phone was already held by another patient (unique index 23505 on every merge). The field now keeps its current value instead (holder check in `mergePvsDataIntoPatient`).
10. **Google OCI:** every failure was final after 3 tries in ~35 s (a minute of Google trouble or a 429 lost the Purchase); duplicates counted as failures; payment dated before the click rejected for good; no EU consent signal; phone hash without "+". Now `ADS_RETRY` (8 retries from 60 s with backoff, ~4 h) for CAPI and OCI, `classifyOciFailure` (already sent / retry / permanent), conversion time clamped into [click + 1 min, now], `consent.adUserData = GRANTED` (only sent with the person's ads consent), Google phone hash = sha256("+" + E.164 digits). **Meta CAPI:** phone hash was the national number with leading 0 (never matches); now E.164 digits with country code (default 49).
